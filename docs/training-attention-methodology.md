# Replay attention по версиям KV-блоков: методология и границы эффективности

## 1. Постановка задачи и выбранная схема

Нужно дифференцируемо пересчитать записанную генерацию с изменяемыми cache views.
Каждый запрос должен видеть ровно те вхождения токенов, которые были доступны
при его исходном выполнении, и использовать те же относительные координаты RoPE.
Порядок токенов в упакованном тензоре сам по себе эту информацию не задаёт.

Рассматриваемая схема:

**одна задача на логическую версию KV-блока → FA4 varlen с маской исторической
видимости → дифференцируемый CuTe DSL merge частичных outputs и LSE.**

Это практический кандидат на готовом FA4 API. Глобальная оптимальность и
превосходство по времени не доказаны; результатов бенчмарка в этом документе нет.
FA4 и merge исполняются как CUDA-ядра, скомпилированные из CuTe DSL.

## 2. Обозначения

| Символ | Значение |
|---|---|
| $N$ | Число исходных токенов и исходных строк Q/K/V |
| $C$ | Число обрабатываемых логических **версий** KV-блоков |
| $K_c$ | Число KV-вхождений в упакованном диапазоне версии $c$ |
| $Q_c$ | Число чтений этой версии; повторные чтения одним запросом считаются отдельно |
| $T=\sum_c K_c$ | Суммарное число упакованных KV-вхождений |
| $R=\sum_c Q_c$ | Суммарное число экземпляров Q и частичных outputs |
| $E$ | Число разрешённых пар Q–K с учётом кратности вхождений |
| $W=\sum_c Q_cK_c$ | Число пар в полных прямоугольниках «читатели версии × её KV» |
| $G$ | Число задач при разбиении чтений на обычные causal/full-группы |
| $P=\sum_{g=1}^{G} k_g$ | Сумма длин KV-диапазонов этих групп, включая перекрытия |

$C$ — не обязательно число одновременно живых блоков: замены и копирования
могут создавать дополнительные версии. Если логические блоки не перекрываются
и не содержат исторических копий, $T=N$. Оценка $R\le NC$ требует, чтобы каждый
запрос читал каждую версию не более одного раза. В общем случае кратность чтений
сохраняется, поэтому $R$ может быть больше $NC$.

В формулах сложности ниже число голов и их размер фиксированы. Если учитывать
их явно, KV занимает $T H_{\mathrm{kv}}(d_k+d_v)$ элементов, Q — $R H_qd_k$,
а частичные outputs — $R H_qd_v$. LSE хранится в FP32 по одному значению на голову.

## 3. История видимости не равна порядку упаковки

Пусть A читает себя, а B читает A и себя. Генерация и последующая упаковка:

~~~text
Время:       a1 a2  ->  b1 b2  ->  a3  ->  b3

Упаковка:   [ a1 a2 a3 | b1 b2 b3 ]
                 A          B

                  ключи
              a1 a2 a3 | b1 b2 b3
запрос b1      +  +  . |  +  .  .
запрос b2      +  +  . |  +  +  .
запрос b3      +  +  + |  +  +  +
                     ^
             a3 ещё не было для b1 и b2
~~~

У `b3/a3` дыры нет: a3 появился раньше b3. Стандартная causal-маска по
упакованным индексам ошибочно разрешила бы a3 для b1 и b2.
Для чтений B → A достаточно сохранить длины `[2, 2, 3]`.

Обычная causal-маска FA с выравниванием по правому нижнему углу задаёт
$j\le i+K-Q$. Она выражает последовательное увеличение видимого префикса,
но не произвольную историю роста. Например, история `[2,2,4,4,6,6]` содержит
повторы и скачки; её нельзя представить одним таким треугольником без
дополнительных преобразований.

## 4. Точная семантика чтений и RoPE

Для запроса $i$ каждое чтение $r$ задаётся версией $c(r)$, интервалом
$[\ell_r,u_r)$ и относительной позицией запроса $p_r$. Пусть
$\sigma_c(j)$ возвращает исходную строку K/V для логической позиции $j$ версии
$c$, а $t_{cj}$ — координату её ключа. Для одной головы:

$$
s_{irj}=\alpha
 \left\langle R(p_r)q_i,\ R(t_{c(r)j})k_{\sigma_{c(r)}(j)}\right\rangle,
\qquad \ell_r\le j<u_r.
$$

Здесь $R$ — оператор RoPE, $\alpha$ — attention scale. Полный softmax берётся
по **всем разрешённым вхождениям**, а не по множеству уникальных исходных строк:

$$
o_i=
\frac{\sum_{r\in\mathcal R_i}\sum_{j=\ell_r}^{u_r-1}
            e^{s_{irj}}v_{\sigma_{c(r)}(j)}}
     {\sum_{r\in\mathcal R_i}\sum_{j=\ell_r}^{u_r-1} e^{s_{irj}}}.
$$

В текстовом случае $t_{cj}=j$, а относительная позиция запроса для явного
чтения блока из cache view равна `total_visible_length - 1 - prefix_before_block`.
Для неявно добавляемого чтения собственного токена используется его отдельная
записанная позиция; она не выводится из отсутствующего в cache view блока.
Для mRoPE используются записанные координаты по трём осям и смещения копий;
видимость при этом по-прежнему определяется интервалом токенов.

### Почему custom mask не позволяет автоматически оставить один общий Q

Маска лишь разрешает или запрещает уже вычисленный score. Она не меняет
поворот вектора Q перед умножением на K.

Для единой фиксированной системы координат потребовались бы позиции $a_i$
для запросов и сдвиги $b_c$ для блоков, удовлетворяющие

$$
p_{ic}=a_i-b_c.
$$

Тогда $\langle R(p_{ic})q_i,R(t_{cj})k_j\rangle
=\langle R(a_i)q_i,R(t_{cj}+b_c)k_j\rangle$.
Это условие согласованности относительных углов для произвольных Q/K;
вырожденные входы и совпадения по периодам RoPE не рассматриваются.

Для приведённой истории координаты имеют вид:

| Запрос | $p_{iA}$ | $p_{iB}$ | $p_{iA}-p_{iB}$ |
|---|---:|---:|---:|
| b1 | 2 | 0 | 2 |
| b2 | 3 | 1 | 2 |
| b3 | 5 | 2 | 3 |

Фиксированное $b_B-b_A$ не может одновременно равняться 2 и 3. Следовательно,
один заранее повёрнутый Q на запрос и одна фиксированная координата каждого K
не воспроизводят эти scores. Четырёх связей между запросами b1/b3 и ключами
a1/b1 достаточно для противоречия даже при произвольных фиксированных
координатах отдельных ключей.

Если общая система координат существует, один глобальный masked attention
действительно становится альтернативой без размножения Q. Это отдельный
частный случай, например неизменяемый префикс A перед растущим B.

## 5. Организация выбранного оператора

Для каждой версии собираются её читатели и один KV-диапазон, покрывающий
используемые позиции. Все исторические границы переводятся в локальные
индексы этого диапазона. Версия блока может ссылаться на несколько исходных
спанов; это не означает повторной упаковки каждого исторического префикса.

~~~text
                     план из истории
          индексы, RoPE-позиции, left/right, cu_seqlens
                              |
         +--------------------+---------------------+
         |                                          |
KV: [ версия A | версия B | версия C ]     Q: [ читатели A | B | C ]
    одна упаковка на версию                  копия на чтение
         |                                          |
         +---------------- gather + RoPE ------------+
                              |
                   один FA4 varlen-вызов
                   mask: left[q] <= k < right[q]
                              |
                   partial outputs + partial LSE
                              |
                   CuTe DSL merge по владельцу Q
                              |
                         итоговый output
~~~

Varlen объединяет последовательности разной длины без padding между ними.
Runtime-маска получает границы через вспомогательные GPU-тензоры; требуется
$O(R)$ чисел, а не матрица $Q_c\times K_c$. При вычислении маски нужно
корректно переводить локальный индекс Q в индекс упакованных метаданных.
В FA4 эти параметры доступны через `mask_mod` и `aux_tensors` в
[обычном и varlen API](https://github.com/Dao-AILab/flash-attention/blob/98c1cee0ed59307833841cdbf567fe336ceec13a/flash_attn/cute/interface.py#L4151-L4268).

Повторное чтение той же версии создаёт отдельное вхождение Q с собственной
позицией, но может использовать те же упакованные K/V. Дедупликация таких
чтений изменяет softmax. Копии блоков сохраняют отображение $\sigma_c(j)$:
градиенты разных вхождений должны суммироваться в исходной строке.

Кэш плана содержит только метаданные. Упакованные активации и повороты
строятся для конкретного слоя и forward, поэтому кэш не удерживает веса
или вычислительный граф предыдущего прохода.

## 6. Объединение partial attention через LSE

Для краткости индекс головы опущен. Для частичного чтения $r$:

$$
Z_r=\sum_j e^{s_{irj}},\qquad
L_r=\log Z_r,\qquad
O_r=Z_r^{-1}\sum_j e^{s_{irj}}v_j.
$$

FA возвращает **нормализованный** $O_r$, а не числитель. Поэтому:

$$
L=\operatorname{logsumexp}_r L_r,\qquad
w_r=e^{L_r-L},\qquad
O=\sum_r w_rO_r.
$$

Для устойчивого forward вычисляются
$m=\max_r L_r$, $z=\sum_r e^{L_r-m}$ и
$u=\sum_r e^{L_r-m}O_r$, после чего $O=u/z$.
Суммирование и нормализацию разумно выполнять в FP32; dtype результата
совпадает с dtype активаций. Реализация в конечной точности требует
отдельной численной проверки, несмотря на точность алгебраического равенства.

## 7. Зачем backward нужен dLSE

Пусть $g=\partial\mathcal L/\partial O$. Производные merge:

$$
\frac{\partial\mathcal L}{\partial O_r}=w_rg,\qquad
\frac{\partial\mathcal L}{\partial L_r}
  =w_r\langle g,O_r-O\rangle.
$$

Первый градиент изменяет результат внутри чтения. Второй изменяет вес
этого чтения относительно остальных. Оба должны попасть в backward FA.

~~~text
loss -> dO -> merge backward
                   |
            +------+------+
            |             |
          dO_r          dLSE_r
            |             |
            +--- FA4 backward ---+
                                 |
                            dQ_r, dK_r, dV_r
                                 |
                    inverse RoPE + суммирование
                    по исходным строкам Q/K/V
~~~

Проверка через производную score: пусть $p_{rj}=e^{s_{irj}}/Z_r$.
Локальный backward с двумя входящими градиентами даёт

$$
ds_{irj}
=p_{rj}\left[
 dO_r^\top(v_j-O_r)+dL_r\right]
=w_rp_{rj}\,g^\top(v_j-O).
$$

Последняя формула — ровно градиент общего softmax. Если убрать $dL_r$,
исчезает слагаемое, учитывающее конкуренцию между чтениями.

Минимальный пример: по одному ключу в A и B, $V_A=0$, $V_B=1$.
Локальные outputs всегда равны 0 и 1 и не зависят от Q/K, но
$O=e^{s_B}/(e^{s_A}+e^{s_B})$. При $s_A=s_B$ и $g=1$:

$$
O=\tfrac12,\qquad dL_A=-\tfrac14,\qquad dL_B=\tfrac14.
$$

Без dLSE локальные Q/K-градиенты были бы нулевыми.
[Backward FA4 принимает `dlse`](https://github.com/Dao-AILab/flash-attention/blob/98c1cee0ed59307833841cdbf567fe336ceec13a/flash_attn/cute/interface.py#L4042-L4106)
и поддерживает нужную цепочку.

В проверенной ревизии
[FA3 backward принимает `dout, *args` и игнорирует LSE-adjoint](https://github.com/Dao-AILab/flash-attention/blob/98c1cee0ed59307833841cdbf567fe336ceec13a/hopper/flash_attn_interface.py#L675-L704).
Вернуть численное значение LSE и поддержать его дифференцирование — разные
возможности. Для внешнего обучаемого merge FA3 потребовал бы дополнительной
реализации этой производной. Обычное обучение с FA3 поддерживается:
оператору attention без внешнего объединения partial outputs такая
дополнительная выходная ветка не нужна.

## 8. Маскинг, batching и асимптотика для C блоков

Ниже считаются вызовы API на один attention-слой в forward, не число
CUDA-ядер. Backward содержит соответствующие обратные операторы.
Память KV в таблице — подготовленные KV-активации; общие исходные входы,
выходы и рабочая память backward учитываются отдельно.

| Маскинг | Упаковка | Вызовы | Подготовленные KV | Основная работа attention |
|---|---|---:|---:|---:|
| Causal/full | Отдельные группы, срезы общих KV | $G$ | $O(T)$ | $O(E)$ |
| Causal/full | Varlen с упаковкой диапазона каждой группы | 1–2 | $O(P)$ | $O(E)$ |
| Custom | Отдельный вызов на версию | $C$ | $O(T)$ | $O(W)$ |
| Custom | Обычный batch с padding | 1 | $O(CK_{\max})$ | $O(CQ_{\max}K_{\max})$ |
| **Custom** | **Varlen по версиям без padding** | **1** | **$O(T)$** | **$O(W)$** |

Оценки относятся к FA-подобному обходу пар/плиток при фиксированных размерах
голов. GPU-плитки, планирование и служебные операции добавляют накладные
расходы. Для custom-строк здесь не предполагается block-sparse skipping.

Q и partial outputs занимают $O(R)$ строк, в padded-варианте —
$O(CQ_{\max})$. Метаданные выбранного плана занимают $O(T+R+C)$.
Merge обрабатывает $R$ частичных outputs за $O(RH_qd_v)$ операций.
Данные RoPE, FP32-накопители и workspace влияют на константы и пиковую память.

В отдельных вызовах обычный срез тензора может быть view общей памяти.
Индексация тензором индексов и `cat` материализуют данные. Varlen сам по себе
не требует дублирования: $P$ растёт только при упаковке перекрывающихся
KV-диапазонов как независимых задач.

Рассмотрим отдельно блок с $L$ ключами и $L$ запросов к нему, где $L$ чётно.
Для истории видимых длин `[2,2,4,4,...,L,L]` простое разбиение на full-группы
даёт $G=L/2$ и $P=2+4+\dots+L=L(L+2)/4=\Theta(L^2)$.
Это пример для данной схемы разбиения, не нижняя граница для всех алгоритмов
attention. Для длин `[1,2,3,...,L]` одна causal-задача уже достаточна.

При фиксированном $C\le10$ и без копий версий $T=N$, а без повторных чтений
$R\le NC$. Подготовленные активации выбранной схемы линейны по $N$.
Переход от $C$ отдельных custom-вызовов к одному varlen-вызову меняет
запуски и распределение работы на GPU, но не порядок $T$, $R$ или $W$.

## 9. Альтернативы с меньшей материализацией

В этой таблице $D$ обозначает размер векторной активации с учётом голов;
точные размеры Q/K/V и outputs приведены в разделе 2. Оценки относятся к
основным активациям; план и рабочая память редукций рассмотрены отдельно.

| Стратегия | Условия | Материализация активаций | Основная цена |
|---|---|---|---|
| Один глобальный FA + mask | Совместимые фиксированные RoPE-координаты; корректно представимая кратность | $O(ND)$ | В общем replay условия не выполняются |
| FA4 по версиям + внешний merge | Нужны готовые varlen, mask и dLSE | $O((T+R)D)$ | Копии Q, partial outputs, потенциально скрытые вычисления |
| Собственное fused-ядро по исходным Q | Поворот Q при обходе версии, адресация спанов, общий online softmax | Цель: исходные $O(ND)$ и итоговые outputs без $O(RD)$ partials | Собственные forward/backward, редукции, динамическая адресация |

В fused-варианте плитка Q обходит разрешённые KV-спаны и меняет локальный
поворот Q при переходе между блоками. Общие максимум, нормализатор и
числитель softmax остаются в регистрах/shared memory; наружу записывается
только итоговый O/LSE. Внешний merge и его отдельный dLSE исчезают:
их математика включена в единый оператор.

~~~text
Исходные Q/K/V + таблица чтений и спанов
                |
        плитка исходных Q
                |
       версия A -> версия B -> версия C
       rotate Q   rotate Q    rotate Q
          \________ online softmax _______/
                         |
                    итоговые O/LSE
~~~

Это устраняет материализацию Q и partial outputs на каждое чтение.
Если K вращается при загрузке из исходных спанов, можно избежать и
материализации логических KV-копий. При предварительном вращении KV
сохраняется дополнительное $O(TD)$.

Остаются метаданные чтений $O(R)$, описания спанов, рабочая память CTA и
workspace для суммирования градиентов. Backward должен восстановить
правильные координаты, кратность и накопление в общие исходные строки.
Лучшая оценка памяти не доказывает меньшую задержку: indirection, вращения
и синхронизация могут ухудшить эффективность Tensor Cores.

При фиксированном C сокращение $O(NCD)$ до $O(ND)$ — уменьшение множителя,
а не нового порядка по N. При растущем C или многочисленных логических
копиях различие уже может стать асимптотическим.

## 10. Где custom mask оставляет запас по вычислениям

Custom mask определяет правильные scores, но сама по себе не гарантирует
пропуск целых скрытых плиток. Например, $L$ запросов записывают блок длины $L$:
первые $L-1$ видят только собственный токен, последний — весь блок. Тогда
$E=2L-1$, но полный прямоугольник содержит $W=L^2$ пар.

Block-sparse расписание или fused-обход видимых спанов может сократить работу
к числу реально посещённых плиток. Частично видимые плитки всё равно требуют
маски. Нужны также стоимость построения sparse-метаданных и совместимость
конкретного режима forward/backward; поддержка подходящей комбинации
varlen, mask, dLSE и sparse-представления должна проверяться отдельно.

Это рассуждение не утверждает универсальную нижнюю границу сложности
точного attention. Оно сравнивает организации FA-подобного вычисления.

## 11. Критерии выбора и будущая проверка

Выбранная схема использует готовое ядро attention и небольшой внешний merge.
Она сохраняет произвольную историческую видимость, разные RoPE-системы
координат и кратность чтений; не материализует отдельный KV-префикс для каждой
исторической длины и не дополняет разные версии до общего размера.
Это основание для выбора прототипа, а не доказательство самой быстрой реализации.

План проверки:

1. Сопоставить разрешённые рёбра, координаты и кратность с независимым
   разворачиванием истории: interleaving, повторные views, копии, очистки, mRoPE.
2. Проверить outputs и dQ/dK/dV с одинаковыми входами и upstream gradient.
   Отдельно проверить singleton-пример dLSE, границы плиток, dtype и checkpointing.
3. Проверить число KV-строк и метаданных при увеличении числа шагов одного
   растущего блока: каждый логический диапазон должен упаковываться один раз.
4. Сравнить отдельные custom-вызовы, custom-varlen и causal/full-группы на
   одной семантике. Измерять полный forward/backward и пиковую память,
   исключив компиляцию и прогрев; фиксировать dtype, формы и загрузку GPU.
5. Исследовать sparse/fused-вариант только при установленном ограничении:
   преобладании скрытых вычислений, materialization traffic или launch overhead.

## 12. Источники и область утверждений

- [FA4 interface, фиксированная ревизия 98c1cee](https://github.com/Dao-AILab/flash-attention/blob/98c1cee0ed59307833841cdbf567fe336ceec13a/flash_attn/cute/interface.py):
  обычный и varlen-интерфейсы, `mask_mod`, `aux_tensors`, `return_lse`, `dlse`.
- [FA4 mask, та же ревизия](https://github.com/Dao-AILab/flash-attention/blob/98c1cee0ed59307833841cdbf567fe336ceec13a/flash_attn/cute/mask.py):
  применение масок и causal-выравнивание.
- [FlexAttention + FlashAttention-4: Fast and Flexible, PyTorch](https://pytorch.org/blog/flexattention-flashattention-4-fast-and-flexible/):
  программируемые маски, block sparsity, CuTe DSL и платформенные ограничения.

Формулы merge, контрпример совместимости RoPE и таблицы сложности выведены
для описанной семантики. Опубликованные benchmark-числа из источников
не переносятся на этот workload.
